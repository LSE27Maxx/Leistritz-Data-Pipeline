## 1. Project Objective

The project is intended to create an automated data pipeline for process-parameter exports generated by the Leistritz extruder.

The intended end-to-end architecture is:

```
Leistritz machine
  ↓
CSV process-parameter export
  ↓
Shared Google Drive
  ↓
Drive → GCS synchronisation
  ↓
Google Cloud Storage
  ↓
Cloud Function ingestion
  ↓
BigQuery raw data
  ↓
BigQuery reporting layer
  ↓
Looker Studio
  ↓
Interactive process-data dashboard
```

The immediate operational objective is to make process data available in a consistent, queryable format for process development, trial analysis and comparison of extrusion runs.

## 15. Current Looker Requirement: Run-Relative Time

This is the most important current development requirement.

Different process files have different actual timestamps. Example:
```
PR1238.csv
17:45:57 → 18:38:07
```

Another sample may have been collected on a completely different date/time.

Plotting `machine_timestamp` therefore prevents intuitive overlay of multiple samples.

The desired behaviour is: each file starts at t = 0 seconds. For each individual file:
```
elapsed_seconds = machine_timestamp - first timestamp in that file
```

Example:
```
PR1238.csv
17:45:57 → 0 s
17:45:58 → 1 s
17:46:00 → 3 s
...
18:38:07 → 3130 s
```

Another file:
```
PR1240.csv
10:12:03 → 0 s
10:12:04 → 1 s
...
```

Both can then be plotted against `elapsed_seconds` rather than their actual dates.

This will allow `PR1238.csv`, `PR1239.csv`, `PR1240.csv` to be overlaid on the same graph.

## 16. Important Design Decision for Run-Relative Time

The run-relative time should preferably be created in BigQuery, rather than relying entirely on Looker calculated fields.

Recommended conceptual calculation:
```sql
TIMESTAMP_DIFF(
  machine_timestamp,
  MIN(machine_timestamp) OVER (
    PARTITION BY source_file_name
  ),
  SECOND
)
```

The exact implementation should be checked against the current reporting-view SQL before modification.

Potential field name: `elapsed_seconds` or `run_elapsed_seconds`.

Recommended: `run_elapsed_seconds` to make its purpose unambiguous.

## 17. Future Looker Design

The intended comparison chart should support:
```
X-axis: run_elapsed_seconds
Y-axis: parameter_value
Breakdown: source_file_name
```

This should allow multiple samples/files to be selected and overlaid. The user should not need to understand the underlying timestamps.

## 18. Time-Window Statistics

A summary table is also being developed.

Desired statistics: Average, Standard deviation, CV %, Maximum, Minimum.

The statistics should be calculated over a user-selected time window.

The initial implementation used text input boxes (Start Time / End Time with `HH:MM:SS`). The approach was then changed toward numeric slider parameters:
```
Start Time Seconds
End Time Seconds
Range: 0 → 86399
where 00:00:00 = 0, 23:59:59 = 86399
```

A helper field was created — "Seconds from midnight" — based on:
```
HOUR(machine_timestamp) * 3600
+ MINUTE(machine_timestamp) * 60
+ SECOND(machine_timestamp)
```

However, this approach is now likely to be superseded by the run-relative time model.

**This is important: do not continue developing the current time-of-day slider implementation without first considering the new run-relative axis requirement.**

The future design should probably use `run_elapsed_seconds` for both chart x-axis and statistics time-window selection. This would make the controls work consistently across multiple files.

## 19. Statistical Requirements

For a selected `source_file_name`, `parameter_name`, and time range, calculate: Average, Stdev, CV, Max, Min.

The statistics should operate on the filtered `parameter_value` records.

Potential future enhancements:
- multiple-file comparison
- statistics calculated separately per file
- combined statistics across selected files
- automatically displaying sample count
- displaying selected time range
- identifying process stability windows

The exact UX should be decided after the run-relative time axis is implemented.

## 20. Key Data-Model Considerations

The current long-format structure is intentional. Do not pivot the raw data into one column per process parameter unless there is a strong reason.

The long format allows `source_file`, `parameter_name`, `parameter_value`, `machine_timestamp` to support arbitrary machine parameters and makes Looker filtering easier.

However, the reporting layer should expose user-friendly derived fields. Likely useful reporting fields:
```
source_file_name
run_id
machine_timestamp
run_elapsed_seconds
parameter_name
parameter_value
```

Potential future field: `run_start_timestamp` — would make it possible to identify the actual start time of each run if required.

## 21. Potential Technical Risks / Technical Debt

Claude should inspect the actual repository/code before making assumptions.

Known areas requiring review:

**A. CSV parsing robustness** — Historical files have produced `non-numeric-data`, `unknown-error`. The parser should be checked for: unexpected headers, non-numeric Pellet IDs, malformed rows, blank values, decimal formatting, timestamp inconsistencies, encoding issues, variable column counts.

**B. Duplicate detection** — Duplicate-file handling currently exists. Claude should verify exactly what constitutes a duplicate. Potential issue: a filename alone may not always be sufficient to uniquely identify a file. Consider whether future duplicate detection should use filename + file generation/modification timestamp + content hash, depending on the actual operational requirements. Do not change this without understanding the current implementation.

**C. GCS file movement** — The ingestion process moves files between `to-be-processed`, `processed`, `failed-processing`. This should be checked for race conditions and retry behaviour.

**D. Cloud Function retries** — The implementation should be checked to ensure retries do not cause: duplicate BigQuery rows, repeated file movement, inconsistent ingestion logs.

**E. Logging** — The ingestion log is useful but should be reviewed for: structured logging, error traceability, retry visibility, source file identification.

**F. Drive sync pagination** — The Drive sync implementation must correctly handle `nextPageToken` and should not assume that one API response contains all files.

**G. Drive sync state** — The sync state mechanism should be inspected for: stale state, deleted Drive files, renamed files, duplicate files, partial uploads, failed GCS copies.

**H. Security** — Claude should review: service account permissions, Cloud Run authentication, Cloud Function permissions, Drive API credentials, Secret Manager usage, public/private service endpoints. Do not broaden permissions simply to make the system work.
