This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A two-stage GCP data pipeline that gets process-parameter CSV exports from the Leistritz-1 machine's Google Drive folder into BigQuery:

1. **`leistritz-drive-to-gcs-sync`** — Cloud Run service. Polls a Google Drive folder for `.csv` files and copies new ones into a GCS "watch" prefix.
2. **`leistritz-csv-ingest-raw`** — Cloud Functions (Gen2) function. Triggered by GCS object-finalize events on that watch prefix; parses each CSV into long-format rows and loads them into BigQuery.

There is no shared code, build system, or test suite between the two services — each is a standalone deployable with its own `main.py` and `requirements.txt`.

## Deployment

Both services deploy from source (Buildpacks), not from a Dockerfile or CI pipeline — there's no CI config in this repo. Redeploys are done directly against project `notpla-machine-data`.

```bash
# leistritz-drive-to-gcs-sync (Cloud Run, HTTP-triggered)
cd leistritz-drive-to-gcs-sync
gcloud run deploy leistritz-drive-to-gcs-sync --source=. --region=europe-west2

# leistritz-csv-ingest-raw (Cloud Functions Gen2, GCS event-triggered)
cd leistritz-csv-ingest-raw
gcloud functions deploy leistritz-csv-ingest-raw --region=europe-west2 --gen2 \
  --runtime=python311 --entry-point=ingest_csv \
  --trigger-bucket=notpla-machine-data \
  --memory=2Gi
```

**Env vars:** `leistritz-csv-ingest-raw` requires `BQ_REPORTING_TABLE=process_parameters_long_reporting_optimised` (added Step 157) and `BQ_RAW_FILES_TABLE=raw_ingested_files` (added Step 158), alongside the pre-existing `BQ_TABLE`/`BQ_LOG_TABLE` — the function will fail to start without either (`os.environ[...]` raises `KeyError`). Both are persisted env vars on the deployed revision, so a plain redeploy (no flags) preserves them same as any other env var; only needed explicitly (`--update-env-vars=...`) if one is ever missing.

**Memory:** `leistritz-csv-ingest-raw` runs at **2Gi** (raised from the 1Gi default in Step 142 — the long-format transform plus the pandas DataFrame it builds for the BigQuery load roughly doubles/triples a source CSV's footprint in memory, and files above ~9 MiB were intermittently exceeding 1Gi and crashing with zero log trace). Don't redeploy without `--memory=2Gi` or this regresses silently.

**Automated Drive sync:** a Cloud Scheduler job, `leistritz-drive-to-gcs-sync-daily` (project `notpla-machine-data`, region `europe-west2`), calls `leistritz-drive-to-gcs-sync`'s HTTP endpoint daily at 06:00 Europe/London using OIDC auth as `462425991200-compute@developer.gserviceaccount.com` (already granted `roles/run.invoker` on that service). This satisfies Priority 5 for new files going forward — added in Step 142.

`gcloud run deploy` / `gcloud functions deploy` without extra flags preserve existing env vars, service account, and resource limits from the current revision — only pass flags when intentionally changing config.

There's no local run/test/lint tooling configured (no Makefile, no test files, no linter config). Validate changes by re-deploying and checking Cloud Logging / the BigQuery log table (see below) rather than via a local harness.

## Architecture: the ingest pipeline

The two functions are decoupled through GCS folder prefixes acting as a state machine, not through direct calls:

```
Drive folder (DRIVE_FOLDER_ID)
  --[drive-to-gcs-sync]-->  gs://notpla-machine-data/<WATCH_PREFIX>/*.csv
  --[GCS finalize event]--> csv-ingest-raw
  --[on success]-->  moved to <PROCESSED_PREFIX>/
  --[on failure]-->  moved to <FAILED_PREFIX>/<error_category>/
```

**`leistritz-drive-to-gcs-sync`** (`sync_drive_to_gcs` in `main.py`):
- Lists all non-folder files in `DRIVE_FOLDER_ID`, paginating via `nextPageToken`.
- Dedup is via per-file marker blobs at `<SYNC_STATE_PREFIX>/<drive_file_id>.synced` — a file is "already synced" purely by marker existence, independent of the CSV's ingest outcome downstream.
- Non-`.csv` files are skipped.

**`leistritz-csv-ingest-raw`** (`ingest_csv` in `main.py`), on each GCS finalize event:
- Ignores events whose object path doesn't start with `WATCH_PREFIX` — this also means **the function re-triggers itself harmlessly** when it moves a file to `PROCESSED_PREFIX`/`FAILED_PREFIX` (those copies fire new finalize events that get filtered out here).
- Checks `already_processed()` — a live query against `ingestion_file_log` for a prior `SUCCESS` row for this exact `source_file` path. This is a check-then-act race: concurrent invocations for the same file (GCS delivers at-least-once) can both pass this check before either logs `SUCCESS`.
- CSV parsing rule (`parse_csv_to_long_rows`): row is skipped if column D (index 3) is blank; every other non-empty column becomes one long-format output row, keyed by that column's header as `parameter_name`. Columns B/C (indices 1/2) are the source date/time and are combined into `machine_timestamp`, not emitted as parameters themselves.
- `load_rows_to_bigquery` is a synchronous blocking load (`load_job.result()`) with `WRITE_APPEND`; the `SUCCESS` log write only happens after this returns without error, and only after the source blob has already been moved to `PROCESSED_PREFIX`.
- `load_rows_to_reporting_table` (added Step 157) runs immediately after the raw load, appending a reduced-column, pre-computed row set (including `elapsed_seconds_from_file_start`/`elapsed_seconds_bucketed_10s`, now computed in Python inside `parse_csv_to_long_rows` from the file's own in-memory rows, not a BigQuery window function) to `process_parameters_long_reporting_optimised`. **This write is deliberately best-effort**: it's wrapped in its own try/except, and a failure there only writes a `REPORTING_TABLE_LOAD_FAILED` line to the text log — it does NOT mark the file `FAILED` in `ingestion_file_log`, move it to `FAILED_PREFIX`, or block the `SUCCESS` path. This is intentional: reliable ingestion (Priority 1) must not regress because of a reporting-table hiccup (Priority 2). The consequence is a small risk of a file having raw data but no corresponding reporting-table rows — recoverable by re-deriving from the raw table if it's ever spotted (grep the text log for `REPORTING_TABLE_LOAD_FAILED`).
- `record_raw_file_present` (added Step 158) runs right after that, appending one tiny marker row (`source_file`, `first_loaded_at`) to `raw_ingested_files` — same best-effort pattern (`RAW_FILE_MARKER_FAILED` on failure, never blocks `SUCCESS`). This table exists purely so `unresolved_failed_files`/`failed_files_resolution_status` can check "does this file have raw data" via a join against ~500 rows instead of a full scan of the raw table — see Known gaps.
- Every outcome (`SUCCESS`, `FAILED`, `DUPLICATE_REJECTED`) is logged to two places: a row in the `ingestion_file_log` BigQuery table (`write_bq_log`, structured, queryable) and an append-only text blob at `LOG_FILE_PATH` in GCS (`write_text_log`, human-readable running log). Failure `error_category` is inferred from substring-matching the exception message (`"timestamp"`, `"non-numeric"`, `"empty"`, `"bigquery"` → known categories, else `"unknown-error"`) — this is fragile if exception wording changes.

## BigQuery layout (dataset `machine_leistritz_1`)

- `process_parameters_long_raw` — one row per (source_file, source_row_number, parameter_name); append-only, loaded by csv-ingest-raw. **Clustered by `source_file`** (added Step 158, metadata-only change via `bq update --clustering_fields`, no rewrite/downtime) — lets a query that filters `source_file IN (<small list>)` prune to just the relevant blocks instead of scanning the whole table; confirmed a real per-file lookup drops from ~26GB to the 10MB billing floor. Still no partitioning, and still expensive for anything that scans broadly without a `source_file` filter (e.g. the old `process_parameters_long_reporting` view's per-query window function, the original Step 157 cost incident).
- `ingestion_file_log` — one row per ingest attempt per file (`status` ∈ `SUCCESS`/`FAILED`/`DUPLICATE_REJECTED`; `IGNORED_OUTSIDE_WATCH_FOLDER` was logged historically but the write for it was removed in a later commit). This table is also read at ingest time by `already_processed()`, so it's both an audit log and part of the pipeline's dedup logic.
- `process_parameters_long_reporting` — a view over the raw table adding `source_file_name` (basename of `source_file`), `elapsed_seconds_from_file_start` (seconds since the earliest `machine_timestamp` for that file, via a window function), and `elapsed_seconds_bucketed_10s` (added Step 153, changed from a 15s to a 10s bucket in Step 154; `elapsed_seconds_from_file_start` floored to the nearest 10-second bucket) for use as a Looker Studio line-chart dimension in place of the raw per-second field. Use this view, not the raw table, for reporting/analysis.
- `raw_ingested_files` — a tiny table (added Step 158), one row per distinct `source_file` that has ever loaded into `process_parameters_long_raw` (`source_file`, `first_loaded_at`), appended to at ingest time by `record_raw_file_present` (best-effort, see Architecture section). ~488 rows. Exists purely so other views can cheaply answer "does this file have raw data" via a small join instead of scanning the 179M-row raw table.
- `unresolved_failed_files` — a view (added Step 146, rewritten Step 158) listing distinct files with a `FAILED` row in `ingestion_file_log` but no `SUCCESS` row and no row in `raw_ingested_files` — i.e. genuinely still-broken files, as opposed to the raw `FAILED`-row count which includes resolved race noise and never shrinks. Currently returns 12 rows (the 4 `PR1216-retest-2/3/4/5.csv` plus the 8 malformed `_HHMMSS_HHMMSS` windowed-export files from Step 152 — the doc's earlier "4 rows" note predated Step 152 finding those). Wired into a Looker Studio scorecard in Step 148. **Step 158 rewrite**: previously did `SELECT DISTINCT ... FROM process_parameters_long_raw` with no filter on every dashboard load (~26GB scanned); now joins against `raw_ingested_files` instead — 20MB (BigQuery's billing floor), same result set, verified identical row-for-row.
- `failed_files_resolution_status` — a view (added Step 149, rewritten Step 158) classifying every *distinct* file that ever logged a `FAILED` row as `resolved` (has a later `SUCCESS` row, or has a row in `raw_ingested_files` despite a lost log write) or `unresolved` (neither — same 12 files as `unresolved_failed_files`). File-grain, not event-grain, unlike the existing `status`-breakdown pie chart on `ingestion_file_log` which counts individual log rows and mixes units with any "how many files are actually broken" question. Currently 191 resolved / 12 unresolved. Data source for the two-slice pie/donut chart added in Step 150. **Step 158 rewrite**: same `raw_ingested_files` join as above — this one didn't respond as well to a narrower `source_file IN (...)` filter against the clustered raw table alone (its candidate list is ~200 files, a large fraction of the raw table's ~488 distinct files, so clustering pruning barely helped, ~26GB → ~12GB) — the `raw_ingested_files` join fixed it the rest of the way, down to 20MB, same as the other view. Verified identical resolved/unresolved counts and file list before/after.
- `process_parameters_long_reporting_optimised` — a **physical, partitioned, clustered table** (added Step 157, replaces `process_parameters_long_reporting` as Looker Studio's data source — see cost-incident note in Known gaps). `PARTITION BY source_date`, `CLUSTER BY source_file_name, parameter_name`. Columns: `source_file_name`, `source_date`, `machine_timestamp`, `source_row_number`, `parameter_name`, `parameter_value`, `elapsed_seconds_from_file_start`, `elapsed_seconds_bucketed_10s` — deliberately narrower than the old view (dropped `source_file` full path, `processed_at`, `source_time`, none of which any known chart uses). Populated going forward by `load_rows_to_reporting_table` in `leistritz-csv-ingest-raw/main.py` at ingest time (best-effort, see Architecture section above); backfilled once historically via `CREATE TABLE ... AS SELECT` from the old view on 2026-09-01 (one-time ~41GB scan, row counts and `elapsed_seconds_*` values verified to match the old view exactly before cutover). The old `process_parameters_long_reporting` view still exists and is still correct — it's just no longer where new elapsed-time math is calculated, and is slated for removal from Looker Studio (not yet done — see Current state).

## Known gaps to be aware of when touching this code

- `already_processed`'s check-then-act isn't transactional — don't assume duplicate protection is airtight under concurrent triggers.
- `SUCCESS` rows in `ingestion_file_log` are not a guarantee the corresponding rows still exist in `process_parameters_long_raw` today — the log reflects the load job's outcome at ingest time only; anything that later modifies the raw table (manual reload, deletion) isn't reflected back into the log.
- Error categorization in `ingest_csv`'s except block is string-matching on the exception message, not on exception type — new failure modes will fall into `unknown-error` unless the matched keywords happen to appear.
- ~~An empty, typo'd dataset `machine_leistrtiz_1` (should be `machine_leistritz_1`) exists in the project~~ — deleted in Step 147, confirmed empty first.
- Historical failed files `PR1216-retest-2.csv` (non-numeric-data) and `-3`/`-4`/`-5.csv` (unknown-error) were never individually diagnosed — worth investigating if the same failure classes recur.
- BigQuery/gsutil gotchas worth remembering: `rows`/`range`/`groups` are reserved words (alias as `n_rows` etc.); `bq query` without `--max_rows` silently caps at 100 rows; `gsutil` treats square brackets (e.g. a filename containing `[WIP]`) as wildcards, and with `-q` the resulting error is swallowed silently; a `CREATE OR REPLACE VIEW` should be confirmed via its `Replaced ...` output, not assumed to have succeeded.
- Looker Studio (`Leistritz_machine_data` report, page "Process Data (Single ID ONLY...)" — name is a holdover from before multi-file support, page itself now does support multi-file overlay): after changing a data source field's type or a chart/control's filter, the **View mode / published report can serve a stale cached render** even though the Edit-mode canvas already shows the fix. A hard refresh (F5) of the View tab resolves it — don't conclude a fix didn't work, or chase a false regression, without refreshing View mode first. Also watch for: (1) a list/dropdown control whose own current selection is fed back as a page filter can create a self-filtering loop that collapses its own option list down to just the selected value — clear the filter chip in the Filter bar to break the loop; (2) a numeric field (e.g. `elapsed_seconds_from_file_start`) can get auto-typed as Date/Time in the Looker data source rather than Number, producing a `Failed to parse input string` error — fix in Resource → Manage added data sources → Edit, not in the chart config; (3) a control/chart's second metric on a numeric field defaults to `SUM` aggregation when added, not `COUNT` — on `source_row_number` (a per-row index in the long-format table, duplicated ~50x per source row across parameters) this produces meaningless huge totals (e.g. "76.7bn" on the `source_file_name` list control, fixed in Step 151 by switching that field's aggregation to Count).
- **A burst of many files landing in the watch folder at once (e.g. a bulk Drive sync) can overwhelm the ingest pipeline in two ways, both now understood** (diagnosed and remediated in Step 142): (1) many concurrent Cloud Function invocations hit GCS's per-object mutation rate limit on the single shared `LOG_FILE_PATH` blob and BigQuery's per-table write rate limit — these show up as `FAILED` rows with `429`/`rate limit` in the error message; (2) the documented `already_processed()` race can let two concurrent invocations both pass the check for the same file, and the loser gets a `404 No such object` trying to act on a file the winner already moved. Neither means data was lost — cross-check `source_file` against both other `FAILED`/`SUCCESS` rows for the same file *and* against `process_parameters_long_raw` directly before assuming a file needs retrying, since a `SUCCESS` row can itself fail to write after a real successful load (see next bullet). When genuinely retrying a batch of stuck files, move them back into the watch folder in small batches (~10) with a pause between batches (~30s) rather than all at once, to avoid re-triggering the same storm.
- **A `SUCCESS` write (`write_bq_log`) can itself fail from the same rate limit, after the file's data has already loaded and the blob already moved to `PROCESSED_PREFIX`.** The exception handler then logs a `FAILED` row instead (its own attempt to move the already-moved file 404s, so `destination_path` is often empty) — meaning a `FAILED` row is not proof a file's data is missing. Always check `process_parameters_long_raw` for existing rows under that `source_file` before reprocessing, or you will duplicate its rows. 13 files were left in this state as of Step 142/143 (real data present, no clean `SUCCESS` log) — backfilled with correct `SUCCESS` rows in Step 144, verified `rows_loaded` against the raw table for all 13.
- **Large CSVs (~9 MiB+ source size) can OOM-crash `leistritz-csv-ingest-raw` with zero log trace at all** — the crash kills the container before any log write (BigQuery or GCS text log) completes, so the file just sits in the watch folder indefinitely with no `FAILED` row to explain why. Diagnose via `gcloud logging read` on the Cloud Run revision directly (look for `Memory limit ... exceeded`), not via `ingestion_file_log`. Fixed in Step 142 by raising `--memory` from 1Gi to 2Gi; re-deploying this function without that flag will regress it back to the default and silently reintroduce the failure mode.
- **245 of 491 total Drive files were never actually reaching the pipeline at all, undetectable from BigQuery/GCS alone** (diagnosed and fixed in Step 152). `leistritz-drive-to-gcs-sync`'s `drive-sync-state/<file_id>.synced` marker blobs are the *only* signal `already_synced()` checks — a marker with content in an old, non-current format (`timestamp | BASELINED | filename | mimetype`, dated 2026-05-25, predating this repo's deployed sync function) existed for 245 files, but no corresponding GCS object had ever been created for any of them. Renaming a file in Drive doesn't change its file ID, so these stayed permanently invisible even after being renamed to their current names (no "BASELINED" prefix visible in today's Drive listing) — a stale marker silently and permanently defeats sync for that file ID, with nothing in BigQuery/`ingestion_file_log` to hint at it since the file never reached the ingest function at all. If files are suspected missing from reporting with no corresponding `ingestion_file_log` row of any status, compare `drive-sync-state/` marker file IDs against a fresh Drive folder listing by ID (not by name) rather than assuming the absence of a marker/log row means the file was never in Drive.
- **`leistritz-drive-sync-sa@notpla-machine-data.iam.gserviceaccount.com` only had `reader` role on the Drive folder, while every human collaborator has `fileOrganizer`/`organizer`** (found and fixed in Step 152, upgraded to `writer`). Google Drive silently blocks `reader`-role identities from downloading/copying any file with `copyRequiresWriterPermission: true` set (a per-file restriction, `403 cannotDownloadFile`) regardless of broader folder access. 198 of the 245 stale-marker backlog files (81%) had this flag set. **`sync_drive_to_gcs` has no per-file exception handling** — one blocked file raises unhandled and crashes the *entire* sync call (visible as an HTTP 500, with everything queued behind that file in the Drive listing never attempted). This was a real, if previously latent, risk for the *ongoing* daily sync too: any new file someone adds to Drive with this restriction would have silently crashed the daily 06:00 job going forward, not just this backlog. Not fixed in code (would need a try/except around the per-file download/upload block in the loop) — worth doing if it recurs.
- **Looker Studio line/chart types cap "Number of points" (Top N dimension values) at 5,000 per chart, and this is a hard platform maximum — not adjustable.** Discovered Step 153: the multi-parameter overlay chart's x-axis (`elapsed_seconds_from_file_start`, one distinct value per second) was silently truncating to the first ~5,000 seconds (~83 min) for any longer-running file, with "Some data excluded" flagged in the Setup tab but easy to miss. Style-tab axis Min/Max were unset — the cap is a dimension-level row limit, not an axis-rendering setting. Fix for any dimension at risk of exceeding 5,000 distinct values: bucket it into coarser increments (e.g. `elapsed_seconds_bucketed_10s`, added Step 153, changed from 15s to 10s in Step 154 — longest file in the dataset currently produces 3,637 distinct 10s buckets, ~1.37x under the cap; a bucket smaller than 10s would need re-checking this margin as files grow) so the chart requests fewer distinct points, rather than trying to raise the limit.
- **A newly-discovered family of malformed source CSVs**: 8 files with `_HHMMSS_HHMMSS` in the filename (e.g. `PR0637_121700_122500.csv`, `PR0111_143900_144500.csv`) — apparently manually-extracted sub-time-window exports — consistently fail `parse_csv_to_long_rows` with "CSV has fewer than 4 columns; cannot apply column D rule". Confirmed genuine (not rate-limit noise) via repeated identical failures on retry. Not investigated further or fixed — would need someone to open one of these files directly to see what's structurally different from a normal export.
- **£204.12 BigQuery cost incident, 24-28 Aug 2026 (root-caused and fixed in Step 157).** `process_parameters_long_reporting`'s window function (`MIN(machine_timestamp) OVER (PARTITION BY source_file_name)`, used to compute `elapsed_seconds_from_file_start`) ran against the *entire* unpartitioned, unclustered `process_parameters_long_raw` table (179.5M rows / 41.3GB) on every single Looker Studio chart/control/filter query, because the calculation lived inside the view rather than being stored. Confirmed directly via `INFORMATION_SCHEMA.JOBS_BY_PROJECT`: 24-28 Aug alone billed ~35 TiB across ~2,548 jobs, individual queries scanning 27-33GB each just to render one filtered chart. Made worse by Step 152's backlog backfill (2026-08-27) nearly doubling the raw table size mid-incident, which is why Aug 27-28 were the worst days. Fixed by: (1) moving the elapsed-seconds calculation into `parse_csv_to_long_rows` in `leistritz-csv-ingest-raw/main.py`, computed once per file in Python from that file's own in-memory rows (no query at all); (2) creating `process_parameters_long_reporting_optimised`, a physical table partitioned by `source_date` and clustered by `(source_file_name, parameter_name)`; (3) `load_rows_to_reporting_table` appending to it at ingest time going forward (best-effort — see Architecture section). **Not yet done: pointing the actual Looker Studio data source at the new table** — no API/CLI access to Looker Studio, this is a manual step for the user (Resource → Manage added data sources → add `process_parameters_long_reporting_optimised` as a new BigQuery data source, re-point every chart/control/filter's data source to it, validate against a couple of known files, then remove/stop using the old `process_parameters_long_reporting`-bound data source). Until that cutover happens, **the underlying cost bug is not actually fixed from Looker's perspective** — the new table exists and is being populated correctly, but Looker Studio is still querying the old expensive view unless and until it's repointed. Also not yet done: a BigQuery custom quota (project-level daily bytes-billed cap — this is the only mechanism that actually enforces a hard stop, a billing budget only alerts) and a billing budget alert (needs Billing Account Admin access, which the ingest/deploy service account here doesn't have — `gcloud billing accounts list` returned zero accounts from this session).
- **3 files in the Drive folder are native Google Sheets, not real CSVs** (`PF1119`, `PF1120`, `PR0917` — no `.csv` extension, `mimeType: application/vnd.google-apps.spreadsheet`). `sync_drive_to_gcs`'s `if not file_name.lower().endswith(".csv")` check correctly and permanently skips these — they cannot be ingested as-is (would need someone to export them to actual CSV from Sheets first, if their content is even meant to be in this pipeline).
